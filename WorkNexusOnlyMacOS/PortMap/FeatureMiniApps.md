# FeatureMiniApps (lib/features/mini_apps → Sources/FeatureMiniApps)

Public entry: `MiniAppsFeature` (`make`, `migrationRegistrar`, `.miniApps(feature)`, `MiniAppHostView(miniApp:)`, `MiniAppsHostStack`, `model: MiniAppsModel` = rail data source, `makeCookieImportModel()`, `startSessionCookies()` / `stopSessionCookies()`).
Views: `MiniAppDialog(feature:existing:onSaved:onClose:)` (add + edit), `CookieImportDialog(cookies:site:source:onClose:)`, `MiniAppSettingsCard(feature:liveLimit:notifyInBackground:dateFormat:onLiveLimit:onNotifyInBackground:)` (all present with `.appDialog`); shared models `feature.cookies` (`CookieImportModel`), internal `trustedModel` / `browsingDataModel`. The rail section lives in `App/Sources/MiniAppViews.swift` (edit, confirm-before-remove, drag to reorder through `MiniAppsModel.move(id:onto:)`); the card is hosted by `App/Sources/Settings/SettingsPages.swift`.
Tabs and Mac apps (new, no Flutter counterpart): see "Tabs" and "Mac apps" below.
Saved passwords, browser-password import and kept session cookies (new, no Flutter counterpart): see "Passwords and sessions" below.
Not ported: Linux web view, Windows-only certificate guard and frame-rate / focus workarounds (WKWebView reports certificate errors itself), the toolbar's developer-tools button (⇧⌘I / F12 and right-click → Inspect Element instead).

## Tabs
Flutter has no tab strip: a page's `window.open` / `target=_blank` goes through `onCreateWindow` (claimed by the link router: dropped; else a 520x720 pop-up). Swift keeps that and adds tabs:
- `MiniAppTabsModel` (one per running app, kept by `MiniAppsModel.tabsModel(for:)`) owns a `MiniAppBrowserModel` per tab (the old per-app browser model is now the per-tab one) — selected tab, new / close / select / next / previous, `maxTabs` = 10 (one web process each; the live-app LRU is unchanged, an app's tabs live and die with it, nothing is persisted). Only the selected tab keeps `lastUrl`.
- Every tab has its own `WKWebView` in the shared `WKWebsiteDataStore` (`MiniAppWebParts.make`), so cookies / sign-in are shared; capabilities (notifications, saved login, permissions, certificates) are per web view through its own bridge. A page-opened tab (`MiniAppWebParts.adopt`) is built from the opener's configuration, so it shares the opener's scripts and bridge and `window.opener` / `window.close()` work.
- A window opened by the page: claimed by the router → nothing; sign-in or sized window → pop-up; link on the app's own site (`IsMiniAppSite`: same host or registrable domain, http(s), not blank) → new tab in front; at the tab limit → pop-up. Middle / ⌘-click on such a link → background tab (⇧ brings it forward).
- Keys (`MiniAppShortcuts` + `MiniAppKeyMonitor`, a local event monitor so ⌘W / ⌘T beat the menu bar): ⌘R / F5, ⇧⌘R / ⌃F5, ⌘L / F6, ⌘[ ⌘] / ⌥← ⌥→, ⌥Home, ⇧⌘I / F12 (private `_inspector`, no-op if absent), ⌘T, ⌘W (the last tab is not closed: the key goes on to the window), ⇧⌘[ ⇧⌘] / ⌃Tab ⌃⇧Tab, mouse back / forward buttons. ⌥← / ⌥→ never take a text field's word-jump (the address field, or a page element that is editable).

## Mac apps
New feature, not a Dart port. macOS cannot embed another app's windows, so the rail also holds buttons that open (or bring forward) an installed Mac app — Slack, Notion, Figma, Xcode… — next to the mini apps, between the last mini app and "Add".
- `NativeApp` (id, name, bundleId, path, position); table `nativeApps` from the new migration `miniapps_v2` (`miniapps_v1` is untouched; both come through `MiniAppsFeature.migrationRegistrar`). `bundleId` is unique.
- Use cases: `AddNativeApp` (reads name — `CFBundleDisplayName`, else `CFBundleName`, else the file name — and `CFBundleIdentifier` from `Contents/Info.plist` through `AppBundleReader`; refuses anything that is not an `.app` bundle of package type `APPL`; the same bundle identifier is never added twice, and when it is added again at another path the existing entry is pointed at the new path, which is how "Locate…" works), `RemoveNativeApp`, `MoveNativeApp` (reorder, same shape as `MoveMiniApp`).
- `NativeAppsModel` (`feature.nativeApps`): list, add / remove / move (also by one step and by drag), `launch` through the injected `AppLauncher` (`WorkspaceAppLauncher`: `NSWorkspace.openApplication` with `activates = true`; an app that already runs is un-hidden and activated), running state from `AppLauncher.events()` (`NSWorkspace` didLaunch / didTerminate), missing state (`exists(path:)`, rechecked when the window comes forward), icons from `NSWorkspace.icon(forFile:)` kept per path, and the installed-apps list for the dialog. No Dock / AppleScript automation, no Accessibility permission.
- Rail: `NativeAppRailButtons` in `App/Sources/NativeAppRailViews.swift` (64x54 `RailLabeledButton`, 22pt icon `NativeAppRailIcon`, running dot, dimmed + tooltip when missing; context menu Open / Reveal in Finder (Locate… when missing) / Move up / Move down / Remove after asking; drag payload `native:<id>` so it never mixes with a mini app's). "Add" is a native `NSMenu` (`RailPopupMenu`): Add website… (`MiniAppDialog`) and Add Mac app… (`NativeAppPickerDialog`: /Applications, ~/Applications, /System/Applications one folder level down, searchable, added ones marked, "Choose other…" with `NSOpenPanel` for `.applicationBundle`).
- Settings: a "Mac apps" section in `MiniAppSettingsCard` (`NativeAppSettingsList`: list, remove after asking, Add Mac app…).
- Not cheap, so left out: ⌘-number / rail focus for Mac apps; locating a missing app as a different app (it is added as a new button instead).

## Passwords and sessions
New features, not a Dart port. Why: a mini app's `WKWebView` has no password AutoFill of its own (the system's Passwords / passkeys need the browser entitlement), a cookie import carries cookies only, and WebKit forgets cookies without an expiry when the app quits. `localStorage` / IndexedDB already persist in the shared `WKWebsiteDataStore.default()`, so a single-page app's token survives a relaunch once the user signed in inside the mini app; importing Chrome's `localStorage` (LevelDB) is out of scope.

**A. Saved passwords (keychain).**
- `WebLogin` (origin = scheme + host + port as `location.origin` spells it, username, password), `WebLoginSummary` (no password: every list and chooser), `webOrigin(of:)`. `WebLoginRepository`; use cases `SaveWebLogin` (same origin + user → updated), `FindWebLogins(for:)` (exact origin only), `ListWebLogins` (no secret read), `ForgetWebLogin`, `NeverSaveForSite`, `ResolveWebLoginOffer` (none / save / update).
- `KeychainWebLoginRepository` over `KeychainItemStore` (`SystemKeychainItemStore`: `kSecClassGenericPassword`, service `com.worknexus.macos.weblogins`, one item per origin + user — account `"<origin> <user>"`, label `WorkNexus: host (user)`, the password as the item's secret). Passwords are nowhere else (no GRDB, JSON, defaults, logs). The never-save list (origins only) is `password_never_save.json`. `MiniAppsFeature.make(secrets:)` picks `.keychain` or `.inMemory()` (tests, demo build): tests never touch the real keychain.
- Page side: `MiniAppPasswordCapability` + `MiniAppPasswordScripts`, main frame only, **in a `WKContentWorld` of its own (`wnPasswords`)**. `MiniAppPageCapability` gained `contentWorld` (default `.page`); `MiniAppBridge` is installed once per world and refuses a call whose world is not its capability's (on top of the token and main-frame checks), and hands the capability the frame's origin as WebKit reports it. The existing notification and ZenTao-login capabilities still run in the page's world (the notification shim has to: it replaces `window.Notification`).
  - Detection: any visible `input[type=password]`, with or without a `<form>`, alone of its kind in its scope (two = sign-up / change, left alone); user name = closest visible text / email / tel field before it; a `MutationObserver` (children + class / style / hidden / type) for forms drawn late or re-drawn; a field switched to text by "show password" stays the password field.
  - Autofill: form appeared → `wnPasswordForm(empty)`; the app (origin from the frame, equal to the web view's) lists the origin's sign-ins: exactly one and the form empty → `WKLoginFiller` calls `__wnFillLogin(origin, user, password, force)` with `callAsyncJavaScript(in: contentWorld)` — native value setter + `input` / `change`, the script re-checks `location.origin`, never submits, never replaces typed text; several → the toolbar chooser opens. `https` or `http`, but only the exact origin the sign-in was saved on.
  - Capture: form `submit`, Enter in the fields, or a click on a button in the form / in a block around a form-less password field (not show / hide, reset, cancel…) → `wnPasswordSubmit(user, password)`; the app shows `MiniAppPasswordSaveBar` ("Save password for <host>?" / "Update…?": Save, Never for this site, Not now). Nothing is kept until Save; the typed password waits in `MiniAppPasswordsModel` (memory, unobserved) for at most 3 minutes.
  - ZenTao's own login page of an account the app holds stays with `MiniAppLoginCapability`: no fill, no offer.
- UI: toolbar key button `MiniAppPasswordButton` (list for the page's origin: fill, delete; opens itself as the chooser), the bar between the tab strip and the page, settings section `MiniAppSavedPasswordsSection` (site + user only, delete one / all, never-save list with "ask again").

**B. Import saved passwords from Chromium browsers.** `ChromiumLoginReader` reads the profile's `Login Data` (and `Login Data For Account`) through `readSQLiteSnapshot`, decrypts `password_value` with the "<Browser> Safe Storage" key the cookie reader already holds (`ChromiumCookieReader.crypto(for:)`, so no second keychain prompt; v10 / v11, no domain-hash prefix), skips `blacklisted_by_user`, empty and non-web rows. `LocalBrowserLoginRepository` maps refusals like the cookies (`CookieReadRefusal`). `ImportBrowserLogins` keeps only the sign-ins whose origin's registrable domain is among the PICKED sites. The cookie dialog has an opt-in checkbox (off by default, reset with every profile, hidden for Firefox / Safari); the toast says "Imported N cookies and M passwords".

**C. Session cookies kept between runs.** `SessionCookieKeeper` (`feature.startSessionCookies()` / `stopSessionCookies()`): at launch `RestoreSessionCookies` puts the kept cookies back (only those of the sites still kept, never over one the web view has) and a mini app's first page waits for it (`MiniAppWebParts.make`, 5 s at most); then every `WKHTTPCookieStoreObserver` change is followed 2 s later by `SnapshotSessionCookies` (written only when the session cookies changed), and once more as the app quits (an empty answer then never wipes the copy). Kept sites (`SessionCookieSites`): the mini apps' and the imported sites', by registrable domain (`cookieSite(of:)`). ONE keychain item (`com.worknexus.macos.websession` / `session-cookies`, JSON). Dropped when a mini app is removed, an imported site forgotten, a site's data cleared, and on "clear all browsing data". App glue: `CompositionRoot.init` (start, right after the feature is built so it precedes every page) and `AppDelegate.applicationShouldTerminate` (`.terminateLater`, 1.5 s at most).
